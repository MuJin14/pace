# 跑步核心链路

本项目最关键的链路：界面再漂亮，定位不准或丢数据就等于产品废了。

## 跑步核心链路（曾有一批"让用户白跑"的缺陷，已修）
**这是全项目最关键的链路**：界面再漂亮，定位不准或丢数据就等于产品废了。
以下每条都曾经真实存在，修复要点与理由必须保留。

### 定位与距离（"定位不准"的真实原因）

- **必须按精度过滤**。手机在楼下/树荫/高楼间误差常到 20-50 米，这种点会让轨迹
  "跳出去又跳回来"，一次抖动凭空产生上百米。
  客户端阈值 30 米（`TrackSampler.maxAccuracyMeters`），服务端 35 米（`GpsUtil.MAX_ACCURACY_METERS`）。
  修复前后端都用原始轨迹算距离，**实测一条 340 米的路线能被脏点算成 2000+ 米**。
- **判定口径必须与成绩口径一致**：`ActivityServiceImpl` 用 `totalDistanceMetersFiltered`
  作为成绩，反作弊的「平均速度」也用同一个值。曾出现成绩用过滤值、判定用原始值的矛盾，
  结果一段 GPS 漂移把平均速度推到 100+ km/h，**正常跑步被判超速作弊、不计成绩**。
- 规则集中在 `lib/features/activity/utils/track_sampler.dart`（纯函数、可单测），
  页面不再各写一份，避免"页面能跑但规则和测试不一致"。
  **前端与后端必须同算法**（`TrackSampler` ↔ `GpsUtil`），改一边就要改另一边。

### 🐞 已踩过的坑：「运动记录距离为 0」（走路的人全为 0）

**症状**：部分账号的运动记录距离显示 0，看起来像"某些账号有问题"。

**真实根因**：不是账号问题，是**速度**问题。旧判据是逐段阈值：

```
位移 >= 2 米  →  计入
位移 <  2 米 且 间隔 >= 5 秒  →  计入
否则丢弃
```

而 **geolocator 在多数机型上是 1 秒采样**，于是：

| 速度 | 单段位移（1 秒） | 结果 |
|---|---|---|
| 慢走 1.4 m/s | 1.40 米 | ≥2? 否，间隔≥5s? 否 → **丢弃** |
| 慢跑 2.0 m/s | 2.00 米 | 严格小于 2 也算否 → **丢弃** |
| 跑步 3.0 m/s | 3.00 米 | ≥2? 是 → 计入 |

**每一段都被丢弃 → 距离累加恰好为 0**。
所以「走路的人全为 0、跑步的人全部正常」——这才是"部分账号"的真相。

还有第二个成因：累加基准用的是「上一个**被采信**的点」。连续拒绝时基准被冻结，
后续位移都被同一个远点衡量，进一步锁死为 0。

**修复**：改用**滑窗方向一致性**判据（`COHERENCE_WINDOW_SECONDS = 5.0`、
`MIN_STRAIGHTNESS = 0.6`）：

- 5 秒窗口内分别累计「净位移」与「路径长度」，比值 ≥ 0.6 才算真实移动；
- 真实走直线 → 比值接近 1 → 计入；静止抖动来回漂移 → 路径长度不断累加、
  净位移被限制在抖动幅度内 → 比值很低 → 滤掉；
- **判据对速度不敏感**，因此慢走与快跑一视同仁，也不会因采样间隔从 1 秒变 5 秒而翻盘。

**实测（120 秒行程，期望 = 速度 × 120）**：

| 速度 | 1s 采样 | 2s | 3s | 5s | 10s |
|---|---|---|---|---|---|
| 0.6 m/s | 72 | 80 | 80 | 72 | 72 |
| 1.4 m/s | 168 | 160 | 160 | 168 | 168 |
| 3.0 m/s | 360 | 360 | 360 | 360 | 360 |

**已知下限**：< 0.6 m/s（比散步还慢）时 5 秒窗口净位移太小、无方向性，
会被当成原地漂移。这是明确的取舍 —— 用「暂停」按钮处理站立不动，
比让慢走用户白跑一次好得多。

回归测试：后端 `GpsUtilSlowWalkTest`（6 个）+ `GpsUtilRealTrackTest`（4 个，
用**生产库导出的 520 点真实轨迹**验证新算法与历史值一致）+ 前端 `run_tracking_test.dart`
的「慢走/短间隔不能算出 0」组。

### 历史坏数据的修复（`/api/v1/admin/maintenance/repair-distance`）

**为什么需要它**：算法修复**只对新运动生效**。库里已经存下的记录 `distance_meters`
仍是当初算错的 0 —— 用户看到旧记录还是 0，会认为「根本没修好」。轨迹 JSON 还在，
所以可以用新算法重算。

**为什么不能只改 `activity` 表**：距离被三处聚合吃掉了，
只改原表会变成「记录对了但排行榜还是错的」——数据自相矛盾比不修更糟：

| 聚合 | 表 | 修复方式 |
|---|---|---|
| 累计里程/次数 | `user_stats` | 相关子查询按 `activity` 重算 |
| 日/周/月/rolling30d 榜 | `leaderboard_stats` | **先删 period 再按 activity 重新聚合** |
| 目标进度 | `user_goal` | 按目标区间内的有效运动距离求和 |

**关键设计**（都有测试固化）：

- **全部「先删后重算」**，结果只由 `activity` 唯一决定 → **幂等**，
  可以安全重复执行（第二次 `fixedActivities = 0`，聚合值不变）。
  不用「把差额加回去」：那要求逐条确认该记录当初有没有真正写进聚合表，
  而历史 bug 可能同时影响了写入链路，对账既脆弱又难验证。
- **`dryRun=true` 预演**：只统计不写库。这是一次不可逆的批量改写，
  执行前必须先看影响面。
- **单条脏数据不中止整批**：轨迹 JSON 解析失败只记 `unparsableTracks` 并跳过；
  没有轨迹的记录**保持原样**（不猜、不猜错）。
- **只重算能推导的字段**：刻意**不碰** `weekly_goal_completed_count` ——
  那是「完成周目标」这一过程的结果，无法从 activity 反推，重算会把用户成绩抹掉。
- **整体一个事务**：中途失败整体回滚，不留半成品。
- **`invalid = 1` 的记录不参与聚合**（与榜单口径一致）。

**实现注意（踩过的坑）**：

- 聚合 SQL 一律用 `CAST(x AS DATE)` 而不是 MySQL 的 `DATE_FORMAT()` ——
  后者在 H2（测试库）里不存在，会让整个测试跑不起来。
- 用 `GROUP_CONCAT` 造测试轨迹时记得 `SET SESSION group_concat_max_len`，
  默认 1024 字节会把 JSON 截断成非法 JSON（我因此造出过一条坏数据）。
- 修复逻辑放在 Java 服务里而不是写成 SQL 脚本：它要用到**新版本的距离算法**，
  SQL 里重写一遍等于维护两套算法，一旦漂移就会重演
  「成绩用过滤值、判定用原始值」那类事故。

**用法**：

```bash
# ① 预演（不写库）
curl -X POST "http://<host>:8080/api/v1/admin/maintenance/repair-distance?dryRun=true" \
     -H "Authorization: Bearer <ADMIN 的 access token>"
# ② 确认 fixedActivities 符合预期后正式执行
curl -X POST "http://<host>:8080/api/v1/admin/maintenance/repair-distance?dryRun=false" \
     -H "Authorization: Bearer <ADMIN 的 access token>"
```

回归测试：`DistanceRepairServiceImplTest`（7 个，H2 集成测试，含
`dryRun` 不写库 / 幂等 / 脏数据不中止 / `invalid` 不污染榜单 / 无轨迹不猜值）。
另在**真实 MySQL 8.4** 上逐条实测过全部 7 条生产 SQL 语句。

### 反作弊（曾把正常跑步整单作废）

- ⚠️ **加速度不能用「段速度 ÷ 段时长」算**。GPS 采样间隔在 0.2-1 秒波动，
  按那个写法**正常跑步（3 m/s、间隔 0.3 秒）会得出 10 m/s²，撞上 8 m/s² 阈值**，
  骑行更快几乎必然命中。正确做法是速度变化率 `|v2-v1| / Δt`，
  并要求 `Δt ≥ 0.4s`（更短的时段速度噪声过大，不参与判定）。
- 重复时间戳的位移阈值从 1 米放宽到 5 米：静止时抖 2-3 米是常态。
- 精度差的点不参与反作弊判定 —— 脏点本来就该被距离计算忽略，拿它判作弊会误伤用户。
- **已知局限**：定长采样下的瞬移主要由 `SEGMENT_SPEED_TOO_HIGH` 抓；
  加速度判定只在采样间隔不规则时起作用。这是合理的，但改阈值前要理解这一点。

### 数据保留（曾整次运动丢失）

- **本地草稿**（`lib/core/storage/run_draft_storage.dart`）：轨迹原先只在内存里，
  切后台被系统回收 / 崩溃 / 手滑返回都会让整次运动**彻底消失且无法恢复**。
  现在每 2 秒落盘一次，重进 App 自动恢复并可继续或直接结束；**上传成功才清草稿**，
  上传失败保留（提示"运动数据已保留，可重试上传"）。
- **用时用墙钟（Stopwatch）而不是"每秒 +1"**：后者在 App 被挂起时停止走时，
  而用户还在跑 —— 时长偏短、配速偏快；更严重的是上报的 `startTime` 由
  `endTime - 累计时长` 反推，会晚于第一个轨迹点，直接触发后端
  「开始时间超出时钟偏差」把整次运动作废。现在用第一个有效点的时间作 `startTime`。
- **返回键确认**（`PopScope`）：跑步中误触返回会丢数据，现在弹确认并提供
  「保留并离开」。`start_run_page` 同时实现了 `WidgetsBindingObserver`，
  从后台回前台时校准计时并立刻存一次草稿。
