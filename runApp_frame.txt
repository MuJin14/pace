校园跑 App 项目设计文档
文档版本：V1.0
编写日期：2026-09-22
项目名称：校园跑（Campus Run）
技术栈：Java + Spring Boot + MySQL + Redis + WebSocket

一、项目概述
1.1 项目背景
校园跑是一款面向高校学生的运动记录与社交 App，旨在鼓励学生走出宿舍、参与跑步和骑行锻炼，并通过排行榜、好友互动和专属模式增加运动的趣味性与持续性。

1.2 核心目标
提供精准的跑步/骑行轨迹记录与运动数据统计。

建立基于专属 ID 的用户账号体系，保障账号安全与社交识别。

实现实时排行榜，激发运动竞争意识。

支持好友添加与即时聊天，构建校园运动社交圈。

设计具有校园特色的“专属模式”，增强用户归属感。

1.3 核心功能
模块	功能
用户体系	注册、登录、专属 ID、个人资料
运动记录	跑步、骑行、轨迹地图、距离/时间/配速
排行榜	周榜、月榜、总榜，按跑步/骑行分类
社交	好友搜索、添加、列表、即时聊天
专属模式	校园围栏、目标挑战、组队接力
个人中心	历史记录、成就勋章、设置

二、技术选型
2.1 总体技术栈
层级	推荐技术	用途说明
移动端	Flutter / React Native / 微信小程序	跨平台开发，一套代码覆盖 iOS 和 Android
后端框架	Spring Boot 3.x	核心业务逻辑、RESTful API 开发
安全框架	Spring Security + JWT	用户认证、授权、Token 管理
数据持久层	MyBatis-Plus 或 Spring Data JPA	简化数据库操作
主数据库	MySQL 8.0	存储用户、运动记录、好友关系等结构化数据
缓存/排行榜	Redis	Sorted Set 实现实时排行榜，会话缓存
实时通信	WebSocket	好友即时聊天、消息推送
地图与轨迹	高德地图 API / 百度地图 API	轨迹渲染、地图标记、路线展示

2.2 技术可行性
Java 生态成熟稳定，Spring Boot 能快速构建可维护的后端服务；MySQL 保障事务一致性；Redis 提供高性能排行榜；WebSocket 实现实时聊天。整套技术栈完全能够支撑本项目从 MVP 到完整上线的全过程。

3.2 架构说明
前后端分离：客户端通过 RESTful API 与后端交互，聊天使用 WebSocket。

分层设计：Controller → Service → Mapper/Repository → Database，结构清晰。

缓存策略：Redis 承担排行榜、会话、热点数据缓存。

安全机制：JWT 无状态认证，BCrypt 密码加密，接口权限控制。

四、功能模块设计
4.1 用户与账号体系
账号：手机号或邮箱，用于登录。

专属 ID：格式 CR-XXXXXXXX（CR 代表 Campus Run），全局唯一，用于社交展示与搜索。

ID 生成策略：

方案一：数据库自增主键 + 业务前缀（简单可靠）。

方案二：雪花算法生成全局唯一 ID（适合分布式）。

密码安全：使用 BCrypt 强哈希加密存储，禁止明文。

个人资料：昵称、头像、学校、院系、运动偏好等。

4.2 运动记录模块
运动类型：跑步、骑行。

数据采集：客户端通过 GPS 持续获取经纬度点。

轨迹处理：

滑动平均法：取最近 3-5 个有效点平均值，平滑轨迹。

道格拉斯-普克算法：去除冗余点，保留轨迹形状。

数据计算：总距离、用时、平均配速、卡路里等。

存储方式：

运动记录表存储概要数据。

轨迹点以 JSON 数组存储简化后的坐标。

地图展示：集成高德/百度地图，实时绘制轨迹。

4.3 排行榜模块（Redis ZSET）
Key 设计：leaderboard:{period}:{type}

示例：leaderboard:weekly:running（跑步周榜）

Score：运动距离（米）。

Member：用户 ID。

更新：完成运动后使用 ZINCRBY 原子增加距离。

查询：

ZREVRANGE 获取 Top N。

ZREVRANK 获取个人排名。

多维度：周榜、月榜、总榜；跑步榜、骑行榜。

4.4 社交与聊天模块
好友关系：

表 friendship：user_id、friend_id、status（待确认/已好友）。

支持通过专属 ID 或手机号搜索添加。

即时聊天：

基于 WebSocket 长连接，服务器实时转发消息。

消息持久化到 MySQL message 表。

字段：发送方、接收方、内容、时间戳、已读状态。

动态圈子（可选）：发布运动打卡，好友点赞评论。

4.5 专属模式
校园围栏模式：限定校园地理围栏内运动才计入成绩。

自定义目标模式：设定周目标（如 20km），追踪完成度并颁发勋章。

接力/组队模式：好友组队累计里程，进行团队 PK。

其他特色：校园路线挑战、学期挑战赛等。

六、关键技术与实现要点
6.1 专属 ID 生成
注册时先插入数据库获取自增 ID，再格式化为 CR- + 8 位数字。

或使用雪花算法生成全局唯一 ID，再拼接前缀。

确保唯一性约束，避免并发冲突。

6.2 密码安全
使用 Spring Security 的 BCryptPasswordEncoder。

存储哈希值，验证时使用 matches 方法。

禁止日志中输出密码明文。

6.3 GPS 轨迹处理
客户端采集原始点，过滤精度差、速度异常的点。

服务端或客户端进行滑动平均、道格拉斯-普克抽稀。

轨迹存储为 JSON，减少数据库压力。

6.4 Redis 排行榜
使用 ZINCRBY 原子更新，避免并发问题。

定期将 Redis 排行榜快照持久化到 MySQL，防止数据丢失。

支持分页查询和个人排名查询。

6.5 WebSocket 聊天
Spring Boot 集成 @ServerEndpoint 或 STOMP。

维护用户与 Session 的映射，实现在线消息推送。

离线消息存入 MySQL，上线后拉取。

七、开发路线与里程碑
阶段	内容	目标
第一阶段（MVP）	用户注册登录（含专属 ID）+ 基础跑步/骑行记录 + 个人运动历史	跑通核心闭环
第二阶段	Redis 排行榜（周榜/月榜）+ 运动轨迹地图可视化	增加竞争与可视化
第三阶段	好友系统（搜索/添加/列表）+ WebSocket 即时聊天	构建社交能力
第四阶段	专属模式（校园围栏、挑战任务）+ 动态圈子 + 勋章成就	形成完整生态

可扩展	服务无状态，可水平扩展；Redis 集群支持

九、总结与可行性分析
本项目采用 Java + Spring Boot + MySQL + Redis + WebSocket 的技术栈，完全能够实现校园跑 App 的全部规划功能。Java 生态成熟、社区活跃，适合快速迭代开发；MySQL 保障数据一致性；Redis 提供高性能排行榜；WebSocket 实现实时社交。整体架构清晰，分层合理，可按照 MVP 到完整版的路线逐步推进。

核心难点：

GPS 轨迹的平滑与抽稀处理。

WebSocket 长连接的稳定性与消息可靠性。

排行榜的并发更新与数据持久化。

建议：从第一阶段 MVP 开始，先跑通用户体系和运动记录，再逐步叠加排行榜、社交和专属模式，最终形成一款功能完善、体验良好的校园运动社交 App。
